# 语音转写质量测量协议

> 建立：2026-10-09　适用：`speech.transcribe` DEBUG 动作（见 `docs/DEBUG-LOOP.md`）
> 目的：把「感觉准确性不高」变成可比较的数字，让识别配置的改动有依据。

## 为什么需要它，以及它不能证明什么

活跃路径只能在**新的一次朗读**里被判断，所以「改配置前后」的对比会把配置和「第二次说的时候语速不同」混在一起。本协议**重跑同一段已保存的音频**，把音频固定住，差异才归因得到配置。

**它不能证明的**：绝对准确率。目前的音频来自用户本人的录音、在本人设备上识别，样本量是 5 条 —— 这是**相对比较工具**，不是准确率报告。不要用它的数字对外声称任何准确率。

## 先明确已知的结构性上限

中英混合**不是可以调好的参数**。查证结论（2026-10-09）：

- `SFSpeechRecognizer` 每次请求只解一个 locale。
- 取代它的 iOS 26 `SpeechAnalyzer` / `SpeechTranscriber` 同样是每个 transcriber 一个 locale，WWDC25-277 通篇未提多语言、混语种或自动语种检测。
- 因此**换 API 不解决中英混合**。可用的杠杆只有两个：`contextualStrings` 偏置，和润色服务的事后修复。

## 五段固定素材

用**任意录音 App 在手机上录**（系统「语音备忘录」即可），不要经过本 App —— 见下面的上传方式，测量音频不需要、也不应该进入 App。参考文本是「你说了什么」的地面真值，自己记下来。

| # | 类型 | 用意 | 例（参考文本） |
|---|---|---|---|
| 1 | 纯中文 | 基线 | 这本书讲的是地方财政如何影响城市发展 |
| 2 | 纯英文 | 英文解码能力 | the author argues that incentives shape outcomes |
| 3 | 中英混 | **核心痛点** | 他说的 incentive 其实是制度设计的问题 |
| 4 | 书名 / 作者名 | `contextualStrings` 命中的目标 | 我在读《置身事内》和兰小欢的写法 |
| 5 | 人名 / 术语 | 稀有拉丁词的崩坏程度 | 凯恩斯和 Keynesian 是同一个词的另一面 |

建议每段 20–40 秒。**越短越要小心**：CER 是除以参考长度，短句里一个字错就显著抬高（实测 5 字参考丢一个标点 = 0.4）。

## 执行

前置：USB 连信任的 iPhone，安装并前台运行最新 DEBUG 构建（见 `docs/DEBUG-LOOP.md` 的自动连接）。

把手机上的录音传到 Mac（AirDrop 即可），放进一个目录，然后写清单 —— **`path` 指向本地文件**：

```json
{
  "clips": [
    {"path": "mixed.m4a",  "file": "mixed.m4a",  "reference": "他说的 incentive 其实是制度设计的问题", "note": "中英混"},
    {"path": "book.m4a",   "file": "book.m4a",   "reference": "我在读《置身事内》和兰小欢的写法",       "note": "书名作者"}
  ]
}
```

跑两轮，**只有 `--contextual-strings` 不同**：

```bash
# 基线：无偏置
python3 Scripts/debug_loop.py transcribe --reference clips.json

# 偏置：传入书名与作者
python3 Scripts/debug_loop.py transcribe --reference clips.json \
  --contextual-strings "置身事内,兰小欢"
```

输出每段的参考 / 实际 / CER，以及均值与完全命中数。

### 为什么用上传而不是在 App 里录

带 `path` 的条目以 base64 上传：设备把它写到系统临时目录、转写完即删。**不产生 Reflection、不写数据库、不落进音频库** —— 测量不会污染你的书和记录，也没有任何需要事后清理的东西。

不带 `path` 的条目改为按**文件名**引用设备上已有的录音（`{"file": "latest"}` 取最近一条），用于重跑 App 里本来就有的音频。这条路径要求音频确实存在于 App 里。

> 注意：`devicectl` 往 App 容器放文件是不可靠的 —— 它没有删除能力，`--destination` 对目录的语义也不稳定（会把目录当成文件名写到同名文件上），且 `info files` 的列表并不完整。**不要用 devicectl 摆弄音频目录**；要跑测量就走上传。

## 判读

- **看均值差，不看单段**。5 段里 1 段的波动不足以说明问题。
- 场景的断言只覆盖**机制**：每段都产出非空转写、且设备回显的 `contextualStrings` 与请求一致。回显是「配置真的到达识别器」的唯一端到端证据 —— 字段丢失不会被记成 PASS。
- **CER 数字是报告，不是断言**。目前没有已确立的质量门槛，凭空设一个阈值就是把测量变回猜测。等跑够几轮基线再定门槛。

## 已知会污染测量的因素

- **服务端 vs 端上**：`requiresOnDeviceRecognition` 默认为关，即允许走 Apple 服务端。服务端模型通常更强，设备联网状况会影响结果，所以要记录当时是否联网。
- 同一台设备重复跑结果应稳定；**换设备或换 iOS 版本后不要把数字直接对比**。
- 音频是 AAC/M4A 有损压缩，转写质量受录音质量影响；录音时离麦克风远近会显著影响结果，五段请用一致的姿势。

## 已验证：偏置确实有效，但只对「识别器词表内」的词

2026-10-09 在真机（iOS 27.0 / iPhone18,3）跑通五段完整流程。下面是**真人录音**（iPhone 语音备忘录，每段 5.5–7 秒照参考文本念一次）的结果。

每段单独念一句，参考文本与录音一一对应。三轮只改 `--contextual-strings`，**音频完全不变**：

| # | 参考 | 基线 | +`置身事内,兰小欢` | +`incentive,Keynesian` |
|---|---|---|---|---|
| 1 纯中文 | 这本书讲的是地方财政如何影响城市发展 | 0.056 | 0.056 | 0.056 |
| 2 纯英文 | the author argues that incentives shape outcomes | `...that **intent** his shape...` 0.208 | 0.208 | `**incentive**` 0.146 |
| 3 中英混 | 他说的 incentive 其实是制度设计的问题 | `**intent**` 0.250 | 0.250 | `**incentive**，` 0.083 |
| 4 书名作者 | 我在读《置身事内》和**兰小欢**的写法 | `**智身室内**和**男晓欢**` 0.375 | `**置身事内**和**兰小欢**` 0.125 | 0.125 |
| 5 稀有术语 | 凯恩斯和 **Keynesian** 是同一个词的另一面 | `**Kenyon**` 0.333 | 0.333 | **`Kenyon` 仍未纠正** 0.333 |
| | **均值** | **0.244** | **0.194** | **0.149** |

0/5 完全命中（每段都还差标点或一个字）。

### 结论

1. **管线可用**：上传 → 设备转写 → 回显配置 → 算 CER → 裁决，五段全程跑通。
2. **偏置有效，且效果精确落在被偏置的词上。** 第 4 段两个词（一个 4 字书名、一个 3 字人名）**同时被纠正**；第 3 段把 `incentive` 加进列表后立刻纠正；未列入的词（第 3/5 段的 `incentive`/`Keynesian` 在无偏置轮）纹丝不动。三轮改动只影响目标词，是干净的单变量对照。
3. **但偏置救不了词表外的词。** 第 5 段 `Keynesian` **就在偏置列表里**，`Kenyon` 依然没纠正，CER 三轮都是 0.333。合理推测（未验证）是 `contextualStrings` 只能把识别器往它的词表内推，**无法凭空造出词表里没有的词**；`incentive` 是常见词所以推得动，`Keynesian` 不是。所以偏置不是万能的专名解药，**别把「加进列表」等同于「一定对」**。
4. **纯英文段暴露的是结构上限。** 基线 0.208、加词后 0.146，仍然是 `The after a goes that incentive shape out comes` —— 这是「zh-CN 识别器解英文语音」本身的失败，偏置只是把其中一个词碰巧拉回来。

### 端上 vs 服务端：几乎无代价（`--requires-on-device true|false`）

> 复现命令：`--requires-on-device false` 强制服务端，`true` 强制端上。**不传该参数时用 App 自己的默认值** —— 默认已改为端上（PRD §21.14），所以不传参数的运行测的是**实际出货配置**。

同一个五段素材，四组配置（音频与偏置列表可控）：

| 配置 | 均值 CER |
|---|---|
| 服务端 · 无偏置 | 0.244 |
| **端上 · 无偏置** | **0.249** |
| 服务端 · 带偏置 | 0.149 |
| **端上 · 带偏置** | **0.149** |

- 端上模式**可用**（zh-CN 端上模型已在本机）。无偏置时五段中**三段 CER 逐字相同**，差异只在第 2 段（0.208 → 0.229）与第 5 段的无关紧要处（`词儿` vs `词儿的`）。
- 带偏置时**均值完全相同（0.149）**，逐段也几乎一致。
- 关键：**偏置的收益在端上完整保留** —— 0.249 → 0.149，与服务端的 0.244 → 0.149 是同样的 −0.10。

**结论：把 `requiresOnDeviceRecognition` 设为 `true` 的准确率代价，在这批素材上测不出来。** 隐私与承诺的账因此可以一笔结清：识别全程不出设备，隐私政策不需要新增外发披露，§21.1 那句「本地优先」从假话变成真话。

**但这条结论的边界要说清楚**：五段、短句、安静环境、本人设备。端上模型相对服务端的差距通常出现在**长音频、嘈杂环境、口音、罕见词汇**上 —— 这些都没有被这批素材覆盖。所以这不是「端上等于服务端」的证明，而是一个足够支持决策的信号：方向明确，且该改动可回退。

**一个新增的失败模式（已定案处理）**：强制端上后，若目标 locale 的端上模型未安装，识别**直接失败**，不退回服务端。

实测确认这是**真实可达状态**，不是理论边界 —— 同一台设备上：

| locale | 端上模型 |
|---|---|
| zh-CN | 有 |
| en-US | 有 |
| ja-JP | **无** |
| zh-TW | **无** |

（端上模型由系统键盘与听写设置决定，App 无法触发下载，所以逐语言存在与否并不一致。）

已实现：

- 规则单点化 —— `SpeechRecognitionAvailability.evaluate(recognizer:configuration:)`。UI 用它决定要不要显示麦克风，provider 与文件转写用它决定要不要启动，两处不可能各判各的。
- 模型不可用时**不渲染麦克风**，原位保留一句说明与可行动路径；每次打开界面重查，模型装上后自动恢复。**不做**静默隐藏（会把可修复的暂时状态变成永久不可知）。
- 识别期兜底 —— `supportsOnDeviceRecognition` 是能力检查而非已安装检查，漏网失败以 `kAFAssistantErrorDomain` 1101 到达，由 `SpeechProviderError.from` 映射为同一条可行动文案；且仅在确实要求端上时才归因于模型。

**未消除的已知风险**：端上模型按需下载而触发下载通常依赖一次服务端识别 —— 硬失败因此可能形成死锁。zh-CN 实测已存在，目标场景不受影响；处置方案记在 PRD §21.14。

### 对下一步的影响

- 「偏置有效 → 值得做段落术语抽取」这个推论**成立且有实测支撑**（第 4 段的双词纠正是最强证据）。术语抽取的投入现在有依据。
- 但收益有上限：只覆盖识别器认得的那部分词。对中文专名的收益**比合成语音那一轮显示的要好**（那一轮没能纠正 `置身事内`），所以中文专名也值得做。
- 纯英文整段失败 → **识别语言可配置**是单独的、优先级不低的一条（现在硬编码 `zh-CN`）。

## 方法论教训：合成语音不能当代理

首次验证用 `say` 生成合成语音跑同一套五段，得到均值 0.395、且**得出过两个错误结论**（「偏置对中文同音字很弱」「真人录音会更差」）。换成真人录音后：均值 0.244，且第 4 段两个词全部纠正 —— 方向相反。

**所以：合成语音只能用来验证管线通不通，不能用来评估偏置效果或估计真实准确率。** 要数字就用真人录音。
